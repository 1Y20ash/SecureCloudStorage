# Phase 4 — Document Version Control & Lifecycle

## Scope

Phase 4 extends the Phase 3B evidentiary foundation with controlled document lifecycle metadata and safe version restoration.

## Lifecycle

Document versions follow a strict forward-only workflow:

```text
Draft -> Reviewed -> Approved -> Archived
```

The application rejects skipped, backward, unknown, and post-archive transitions.

## Version history

Every update remains a separate `DocumentVersion`. A new version stores:

- sequential version number
- stored file reference
- plaintext SHA-256 hash
- previous version hash
- creator and timestamp
- change description
- lifecycle status

Existing versions are never overwritten by a restore operation.

## Restore policy

Restoring a historical version creates a new version using the historical stored file and hash. The new version starts as `Draft`, and its `previous_hash` points to the immediately preceding current version. This preserves an auditable history instead of deleting or rewriting records.

Archived documents cannot be restored.

## Authorization

Lifecycle operations are restricted to users who can manage the case. Case access remains deny-by-default through the existing authorization layer.

## Auditability

Lifecycle transitions and restorations create explicit audit records through the Phase 4 service. Existing SQLAlchemy mutation hooks continue to record the underlying model updates as well.

## Integrity

The existing Phase 3B separation between plaintext SHA-256 and encrypted-storage SHA-256 remains unchanged. Version history stores the plaintext document hash; encrypted storage integrity remains on `StoredFile.encrypted_sha256_hash`.

## Migration

Migration `0007_document_lifecycle` follows `0006_encrypted_storage_integrity` and adds lifecycle metadata without changing existing version rows' file/hash relationships.

## HTTP integration

The lifecycle service is exposed through authenticated POST endpoints:

- `POST /documents/<document_id>/lifecycle` — transition the current version to the next valid lifecycle state.
- `POST /documents/<document_id>/versions/<version_number>/restore` — restore a historical version as a new `Draft` version.

Both endpoints enforce case access and case-management authorization, validate service errors, roll back failed transactions, and return the user to the case view with a clear flash message.

## UI integration

The case detail screen now exposes:

- current lifecycle state
- forward-only transition controls
- required transition/change descriptions
- complete version history
- SHA-256 and previous-hash visibility
- creator/timestamp metadata
- historical-version restore controls with a required reason
- explicit archived immutability messaging
- existing version creation and document-sharing controls
